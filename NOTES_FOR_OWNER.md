- Формат на проводе несовместим с v1 (prologue raywire/2): все клиенты и серверы обновлять вместе.

## Linux-туннель (9 октября, обновлено вечером)
- Архитектура: хелпер `raybridge-tunneld` (Go, импортирует форк Xray как библиотеку, /root/raybridge/linux/helper) работает как systemd-сервис с socket-активацией **без root**: DynamicUser и только CAP_NET_ADMIN/CAP_NET_RAW. C++-канал `app.raybridge/tunnel` в linux/runner говорит с ним по unix-сокету (JSON-строки). Пароль администратора спрашивается один раз (pkexec при установке), дальше не нужен.
- Почему не root: цепочка обходов deny-листа конфига (складывание ключей, userinfo в URL, пропущенные ключи dial и т.д.) показала, что запретить root всё опасное по списку нельзя. Теперь даже полный захват хелпера не даёт записи файлов от root. Конфиг Xray всё равно собирается хелпером по белому списку, пользовательский JSON напрямую не передаётся.
- Доступ: SO_PEERCRED + /etc/raybridge/tunneld.json (allowedUids, edition; файл root-owned), политика перечитывается на каждый запрос. Всё равно: любой процесс пользователя из списка может поднимать/опускать туннель и выбирать исходящий сервер.
- Жизненный цикл: после disconnect процесс завершается, следующий connect поднимает свежий (это заодно лечит утечку dialer-controller в форке proxy/tun, которую иначе исправлять только правкой форка). При 16 соединениях отвечает `busy`.
- Lite: только raywire; Full: все протоколы. Раздельный туннель по приложениям в v1 не поддержан (честная ошибка). Системный DNS (resolvectl) не перехватывается. Профили маршрутизации (RU direct, bypassLan) поддержаны.
- Нет kill switch: если сервис умрёт (OOM/kill), трафик пойдёт напрямую, пока UI не опросит статус. Это описано в README хелпера.
- Что не проверено: реальный путь pkexec/polkit/systemd на живом десктопе (в e2e хелпер запускается от uid 65534 через setpriv в netns), упаковка в .deb/pkg (tool/*.sh принадлежит сессии клиента; инструкции в helper/README.md).
- Раундов ревью было три; после третьего исправляются: нет физического маршрута по умолчанию (петля прокси в туннель), ограничение busy-пути, сохранение ошибки старта в runner, publicIpCheckViaVpn, сообщение о несовпадении редакции, WireGuard-kernel-режим, StartLimit в unit.

## Транспорты raywire (9 октября, день)
Из РФ UDP часто режут, поэтому raywire проверен только поверх TCP-транспортов. Матрица (скрипты: `/tmp/claude-0/-root/ae8c88f2-325b-4eb4-bf65-08853af4bf51/scratchpad/transport/<id>/run.sh`), по каждому 5 проверок: скачивание 50 МБ, half-close, UDP внутри потока, отказ чужому ключу, decoy на мусор. Все пройдены, правок в raywire не потребовалось (две прогонки подряд):

| Транспорт | Результат | Скорость на loopback |
|---|---|---|
| tcp + TLS | 5/5 | ~193 МБ/с |
| tcp + REALITY | 5/5 | ~150 МБ/с |
| ws + TLS (и ws без TLS) | 10/10 | ~134 МБ/с |
| grpc + TLS | 5/5 | ~125 МБ/с |
| httpupgrade + TLS | 5/5 | ~160 МБ/с |
| xhttp (h2) + TLS: packet-up, stream-up, stream-one | 15/15 | ~118 МБ/с |
| grpc + REALITY | 5/5 | ~101 МБ/с |
| xhttp + REALITY (stream-one) | 5/5 | ~116 МБ/с |

Рекомендация: по умолчанию raywire поверх REALITY; запасной вариант tcp+TLS на домене с настоящим сертификатом.
Наблюдения (не баги raywire):
- ws+TLS: внешний слой сам отвечает на «не-websocket» запросы (простой GET / получает 404 от Go вместо страницы decoy), так что свойство «любое неавторизованное соединение видит настоящий сайт» для ws не выполняется. Для ws ставьте перед ним реальный обратный прокси с настоящим сайтом, либо используйте REALITY/tcp+TLS. Аналогично у httpupgrade (простые запросы закрываются без ответа).
- [ИСПРАВЛЕНО патчем укрепления, см. выше] httpupgrade в форке: `transport/internet/httpupgrade/dialer.go` (ConnRF.Read) падает с panic, если сервер шлёт байты сразу после 101 (клиентский процесс завершается), а `hub.go` теряет байты, пришедшие вместе с upgrade-запросом. Через raywire-сервер это не вызывается, но злонамеренный сервер может уронить клиента. Это дефект апстрима; httpupgrade лучше не рекомендовать, пока не исправлено.
- gRPC в Xray помечен как deprecated (в пользу XHTTP stream-up h2).
- `allowInsecure` удалён в форке: самоподписанный сертификат клиент доверяет через `pinnedPeerCertSha256`.
- UDP-транспорты (mkcp, quic, hysteria, xhttp по h3) не проверялись и не рекомендуются из-за блокировок.

- Фильтр replay хранится в памяти: после рестарта сервера перехваченный раньше msg1 можно переиграть в пределах 5 минут.

## raywire/3, раунд 2

Открытые находки ревью раунда 2, которые этот шаг кодом не закрывает. Числа взяты из подтверждённых находок ревью (измерены при ревью, не в этом шаге, если не сказано иное).

1. Открытый HTTP на вход `security: tls` (находка 4, существовало до v3). TLS-слой потребляет байты до raywire. Для обычного HTTP первая запись не TLS, чтение падает с ошибкой не EOF, причина `read`, без байтов. Relay всё равно отдаёт декою пустое соединение, и зонд получает EOF примерно через 0,6–0,7 мс (в логе декоя: `open ... eof total=0`). Тот же запрос на raw TCP получает HTTP 400 от декоя примерно через 0,8 мс. Побайтно точный декой за TLS невозможен. Рекомендация: REALITY или raw TCP для входа, где декой должен отвечать на открытый HTTP.

2. Повтор захваченного msg1 стоит CPU (находки 5 и 6, известный остаточный риск R11). Измерено на 2 vCPU: 32 соединения с 127.0.0.1 повторяют захваченный поток 676 байт, 3618 попыток ушли в relay за 12,1 с, CPU сервера 10,7 с (около одного ядра), примерно 2,9 мс CPU на попытку. Случайные 50-байтные головы: 14941 relay за 12 с, CPU 7,6 с, примерно 0,5 мс на попытку. Лимит 32 на источник ограничивает параллельность, но не CPU: один наблюдатель с записью одного msg1 может занять одно ядро с любого IP.
   Варианты: (а) фильтр повторов по проводной форме R_e (доступна до DH и до ожидания остатка): точный повтор головы отвергается на байте 50 без DH; (б) бюджет CPU на головы, прошедшие проверку тега, по источнику и глобально; (в) принять как остаточный риск.

3. Захваченная голова, посланная отдельно, получает ответ через 10 с (находка 6, R2, известный). Измерено: захваченная 50-байтная голова отдельно получила ответ декоя на 10,010 с, случайная 50-байтная на 0,000 с, случайные 49-байтная и 1-байтная тихие пробы на 10,00 с (R1). Все 400 одиночных битовых переворотов захваченной головы дали причину `tag` на байте 50. Тот же фильтр из п. 2(а), если он записывает головы, прошедшие проверку тега, отвергает уже виденную голову на байте 50 и не ждёт остаток. Тогда ответ приходит сразу, как на случайную голову. Головы, которых сервер не видел, по-прежнему ждут остаток.

4. Парсер ссылки Dart не читает `psk` (находка 9, серьёзность high). Владелец: Клиент. `raywire_uri.dart`, `_parseRayWire` (строка 33), строит outbound из address, port, privateKey, serverPublicKey и padding. В `/root/raybridge/lib` нет ни одного чтения или записи `psk`. Хелпер требует `psk` и отказывает в outbound без него, а `structured_json.dart` тоже не проверяет `psk`. Ссылка с `psk=` молча теряет ключ при импорте, и туннель не поднимается с сообщением «psk в raywire не задан: raywire/3 требует psk». До изменения та же ссылка давала рабочий outbound raywire/2. Нужно: читать `psk` в парсере, писать его в outbound и в structured JSON, проверять при импорте (спецификация 14.4).

5. `go test ./infra/conf` падает в TestGeodataConfig из-за отсутствия `resources/geoip.dat` (находка 31, существовало до raywire). Тест паникует с `stat ../../resources/geoip.dat: no such file or directory`, каталога `resources/` в checkout нет. Что сделать: добавить `resources/` в checkout или пропускать тест, когда файла нет. ## raywire/4: итог (13 октября)

Решение владельца (13 октября): «Делать», то есть привязать тег головы T ко времени. Это закрывает часть R2: захваченная голова, которую сервер не принял, раньше зависала на 10 с на всё время работы процесса. Теперь она ограничена окном по серверному времени.

Что изменилось на проводе (SPEC-v4, раздел 1; проверено по `proxy/raywire/handshake.go`):
- prologue = "raywire/4" (`prologue`, handshake.go); headKeyLabel = "raywire/4 head key", maskKeyLabel = "raywire/4 w1", tagLabel = "raywire/4 head" (блок констант в handshake.go, рядом с prkLabel и fingerprintLabel).
- T = HMAC-SHA256(headKey, tagLabel || S_pub || R_e || W1 || BE64(bucket))[0:16], где bucket = floor(unix_seconds / 300) (`headBucketSeconds` = 300, `headBucket`). Клиент берёт bucket из того же отсчёта часов, что и timestamp в полезной нагрузке Noise (`clientNow` в `ClientHandshake`).
- Сервер (`matchHeadTag`) читает время один раз, считает 6 тегов (бакеты b-1, b, b+1 для psk и previousPsk), сравнивает их все через hmac.Equal без раннего выхода. До тега нет DH, Elligator и Noise. Раньше (committed raywire/3) было 2 HMAC.
- Остальной формат головы не менялся: 50 байт (R_e 32, W1 2, T 16), размеры msg1 и msg2, шаблон Noise, бюджет 10 с.

Что осталось без изменений:
- Метки prkLabel = "raywire/3 psk" и fingerprintLabel = "raywire/3 fingerprint" (блок констант handshake.go). Это устаревшие имена шага извлечения ключа, а не версия протокола. Поэтому PSK, его отпечаток, ссылки клиентов, профили, previousPsk и код ключа панели остаются валидными. Метки памяти seen ("raywire/3 seen dh", "raywire/3 seen client", seen.go:18, 22) тоже не менялись: это локальные ключи, на провод они не уходят.
- Формат PSK, ссылки, имена полей конфига, тексты ошибок и форматы строк лога.
- Допуск таймстампа ±5 минут (maxClockSkew, replay.go:12), память голов 24 ч и 65536 записей (seen.go:27, 33), ротация previousPsk до 14 суток (validate.go:19).

Остаточные риски (SPEC-v4, раздел 3):
- R2 (повтор головы, которую сервер не принял) ограничен окном. Внутри окна поведение прежнее: 10-секундное зависание. После окна такой повтор неотличим от мусорной головы и стоит 6 HMAC, без DH.
- Зонд, знающий PSK и публичный ключ сервера, может вычислить теги для любого бакета. Тег не скрывает от держателя PSK.
- Бакет не секрет и в теге открыто не передаётся. Наблюдатель, который знает, что это голова raywire, из неё ничего нового не узнаёт.
- Клиент со сдвигом часов больше примерно 5 минут не подключится (как и в raywire/3). Нужен NTP. Клиент со сдвигом 5–10 минут может получить reason `tag` вместо `replay`.
- Без изменений относительно raywire/3: R3, R11, copy-first, общий PSK, расстояние до декоя, анализ трафика.

Стоимость: 6 HMAC на каждую голову вместо 2, и всё это до DH. Цифры в BENCH.txt сняты на raywire/3 и не пересчитывались. Поправка к SPEC-v4 (проверено по коду и по тесту tag bucket window). Окно действия головы в SPEC записано неверно. Сервер принимает тег бакета c, когда его бакет b лежит в {c-1, c, c+1}. Значит, голова принимается при серверном времени в [(c-1)·300, (c+2)·300). Это 900 с, но окно начинается за один бакет до бакета клиента и заканчивается через 600 с после начала этого бакета. Если отсчитывать от момента создания головы t, где c·300 ≤ t < (c+1)·300, голова действует от 300 до 599 с (при t = c·300 последняя принятая секунда — 599 с после создания). Не «от 600 до 900 с», как написано в SPEC. Поэтому R2 — не «до 15 минут после захвата», а не более 10 минут после создания головы клиентом (599 с). Пример из теста tag bucket window: голова с клиентским временем testNow+599 принимается на сервере при testNow и действует до testNow+899 включительно, то есть ещё 300 с.
